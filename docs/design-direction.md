# L3の用途と次の比較

2026-09-28時点。今のL3は、制御できるprivate networkで配送と優先度の扱いを変えるための実験基盤。既存プロトコルより速いという結論はまだない。

## 順序なし配送だけでは差にならない

| 方式 | 既にできること | L3で比較すべき点 |
|---|---|---|
| TCP | 信頼性と接続内の順序保証。短文と大量転送を別接続に分けられる | 1接続だけを相手にせず、2接続も比べる |
| SCTP | メッセージ境界、信頼性付きのunordered配送、複数stream | unorderedの機能差を優位性と呼ばない。interleavingとschedulerの条件も揃える |
| QUIC | stream間の順序待ちを分離。暗号化・輻輳制御も持つ | メッセージごとのstreamまたはクラス別streamを使い、同じ配送保証で測る |
| Homa / SIRD | 受信側主導の送信量調整と、短文・混雑への対処 | 単純な受信窓だけで同等と扱わない。送信側と共有リンクも混雑する |

仕様の根拠: [SCTP unordered](https://www.rfc-editor.org/rfc/rfc9260.html#section-6.6)、[SCTPのinterleavingとscheduler](https://www.rfc-editor.org/rfc/rfc8260.html)、[QUICのstream間配送](https://www.rfc-editor.org/rfc/rfc9000.html#section-13)、[Homaの送信許可・優先度・再送](https://github.com/PlatformLab/HomaModule/blob/main/protocol.md)、[SIRDの送信側と共有リンクの扱い](https://www.usenix.org/conference/nsdi25/presentation/prasopoulos)。QUIC DATAGRAMは再送しないので、信頼性付きL3の直接の比較対象にはしない。[RFC 9221](https://www.rfc-editor.org/rfc/rfc9221.html)

## 面白さを出すなら、混雑中の扱いを変える

第一候補は、ログ・画像・ファイルを流している最中にも、操作・RPC・制御の短いメッセージを早く届ける用途。平均Mbpsだけでなく、短文のp99、期限に間に合った割合、大量転送の帯域、CPUを一緒に見る。短文だけが速くても、大量転送が止まる方式は採用しない。

ただし、送信プロセス内の優先度だけでは、その先のFIFOに溜まったパケットを追い越せない。次の設計では、受信側の空きと送信側の混雑を交換し、送り出す前に量を調整する。SIRDが扱う共有リンクの競合も検証対象にする。既存の`bytes_per_second`は固定上限であり、空き帯域を推定する仕組みではない。

第二候補は「新しい状態が届けば古い状態は不要」という配送。センサ値や座標更新をキーごとに置換し、古い状態の再送が帯域を使い続けるのを防ぐ。ただし、現在のreliable配送に黙って混ぜない。`delivered / superseded / expired`を呼び出し側へ返す別の配送契約が必要になる。

amitokiの解析用途なら、各中継点の待ち時間・破棄理由・経路を追える計測も相性がよい。パケット処理のStageと組み合わせて、どのキューで短文が遅れたかを可視化できる。これは次の実装候補で、今回のバイナリにhop別traceは入っていない。

## 今回直した土台

- 下位キューの受付後に送信試行と再送予算を確定する。満杯で入らなかった本文は初回送信のまま保持する。
- 受付済みのACK・READY・RESETは、時計精度と絶対期限に依存させない。時計世代、送受信者、session、channel、受信epochは照合し、各キューの滞留時間とhop数は制限する。新しいDATAとOPENは引き続き同期と期限を検証する。
- ACKから往復時間と変動幅を求め、再送待ちを調整する。再送済みの本文はどの送信への応答か分からないのでRTTの推定から除く。初期20ms、下限2ms、上限1秒、損失時は指数backoff。再送予算は維持する。これはRTT推定であり、輻輳制御の実装ではない。[RTT推定の標準的な考え方](https://www.rfc-editor.org/rfc/rfc9002.html#section-5)

## 次の実験で採否を決める

現在の実測対象はL3とLinux TCP。SCTP・QUICの実測はまだない。

1. SCTP unordered / stream別ordered / interleaving、QUICのメッセージ別・クラス別streamを追加する。接続準備込みと確立後を分け、暗号化コストも明記する。
2. 短文64〜256Bと大量転送を混ぜ、回線使用率50/80/95/110%、RTT、損失率を変える。3送信者からの集中と、送信側の共有回線も含める。
3. 同じ本文と配送保証で全件の正常性を確認し、短文p99/p99.9、期限内率、goodput、CPU、再送量を集計する。少数の成功試行だけで速さを判断しない。
4. 通常負荷を悪化させず、混雑条件で既存方式より短文の遅延を下げられる場合に、受信側主導の調整を採用する。効果が出なければ機構を増やさず、解析・障害注入の実験基盤として育てる。
