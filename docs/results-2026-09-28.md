# リポジトリ分離後の比較と改善

前回のL3で未完了だった7試行は、送信キューの受付連携とACKの時計依存を直した後、同じ60試行ですべて完了した。再送待ちをRTTから調整する版も60/60完了。最終確認でも802,800件すべてを配送し、受付確認まで終えた。

本体SDKから使えるL3プラグインも追加した。以下の性能値はL3 CLIを直接使った比較であり、stdio・補助プロセス・フレーム再構成を含む本体プラグインの速度ではない。

## 条件

Xeon Gold 6242、Linux 7.0.0-31、x86_64。同一ホストの2つのnetwork namespaceを内部Docker Ethernet bridgeで接続し、CPU 0/1を割り当てた。CPUの排他的な予約はしておらず、ホスト上の他プロセスは停止していない。両端のTSO/GSO/GROを無効化した。

各条件は3秒×3反復。L3のunordered/ordered、TCP CUBICの1接続/クラス別2接続を比較。本文、予定レート、受信ログ、内容照合を揃え、共通CLOCK_BOOTTIMEで「生成予定時刻→受信アプリ配送」の時間を測る。接続と時計同期の準備を含む。L3の時計基準は受信ノード。同期を省略した測定ではない。

混雑条件は短文128Bを100件/秒、大量転送1200Bを1500件/秒。送信側の外部FIFOを10Mbps・片道1ms・512パケットへ制限する。損失条件は大量転送を500件/秒に下げ、1%のランダム損失を加える。逆方向は制限しない。損失位置は方式間で一致させていない。方法の詳細は[比較手順](../tcp-comparison.md)。

## 最終結果

数値は各試行で求めたp99やgoodputの、3回の中央値。全方式・全条件で3/3完了。

| 条件 | L3 unordered | TCP 1接続 | TCP 2接続 |
|---|---:|---:|---:|
| 短文64B・1万件/秒：p99 | 1.233ms | 1.153ms | 1.154ms |
| 1200B・1万件/秒：goodput | 96.000Mbps | 96.001Mbps | 95.977Mbps |
| 10Mbps混雑：短文p99 | 127.268ms | 270.574ms | 168.801ms |
| 同条件：goodput | 8.532Mbps | 9.300Mbps | 9.277Mbps |
| 同条件：CPU時間/配送件数 | 168.312µs | 90.103µs | 102.250µs |
| 1%損失：短文p99 | 2.648ms | 4.325ms | 12.453ms |

混雑時の短文p99はTCP 2接続より約25%短くなったが、goodputは約8%低く、CPU時間は約65%多い。短文が20ms以内に届いた割合もL3で2%、TCP 2接続で中央値1.33%にとどまった。現状のまま低遅延用途に十分とは言えない。

L3の短文p99は混雑条件で127.191〜127.784ms、TCP 2接続は166.978〜169.030msだった。通常時はTCPのp99がやや短い。1%損失の値は試行ごとの欠落位置に左右されるため、3回だけで普遍的な優位性とは扱わない。SCTP・QUICの実測はまだない。

## 何が改善したか

修正前はL3が23/30完了、TCPが30/30完了だった。[修正前の記録](../tcp-results-2026-09-28.md)はそのまま残した。

キュー/ACK修正版では、L3とTCPがともに30/30完了。下位キューに入らなかった本文を「送信済み」と数えず、時計の精度が悪くても正しい世代・session・epochの受付確認は処理するようにした。

その後、RTTから再送待ちを調整した。混雑条件のL3 unorderedの再送件数は、固定20ms版の392/392/393件から、最終版の129/133/140件へ減った。失われたACKやDATAの回復を保ちながら、混雑による遅延をすぐ損失と扱う再送を減らせた。ネットワークの送信量自体を調整する輻輳制御は、まだ実装していない。

## 時計依存の切り分け

同じ最終バイナリで、混雑条件のL3 unorderedだけを共通時計の直接利用に変え、3秒×3反復した。14,400件すべての配送・受付確認が完了。短文p99の中央値は69.314ms（69.257〜69.336ms）、goodputは9.071Mbpsだった。標準の時計同期を使う127.268msとの差から、時計同期に依存する送信制御も遅延の一因と考えられる。ただし同期通信も同時に除いており、精度判定の待ち時間そのものは計測していない。

一方、短文の再送は各試行423〜424件へ増えた。短文チャネルでRTT推定に使えたACKは、各試行とも最初の1件だけだった。再送済みメッセージのACKを推定から除くため、混雑後のRTTを学習できず、再送待ちが約3.8msのまま残るケースがある。単に同期を外すだけでは、この問題は解消しない。

この診断は同一ホストの共通CLOCK_BOOTTIMEを使うため、別マシン間や通常のプラグインでは使えない。標準結果に置き換えない。生ログは`artifacts/l3-tcp/2026-09-28/final-local-clock/`、集計はJSONの`final-local-clock`に保持した。

```bash
python3 comparison/reliable.py \
  --directory artifacts/l3-tcp/local-clock-diagnosis \
  --workload mixed_10mbps --mode l3_unordered \
  --clock-mode local --duration-ms 3000 --repetitions 3
```

送信プロセスの優先キューを出た後に外部FIFOへ蓄積すると、短文もそこで待つ。今後は送信量調整に加え、信頼性配送の時計依存と、RTT試料を得られないときの再送待ちを切り分ける。[既存方式との比較と用途候補](design-direction.md)に、受信側と送信側の両方を見る案、状態更新の置換配送、SCTP・QUIC比較の条件をまとめた。
